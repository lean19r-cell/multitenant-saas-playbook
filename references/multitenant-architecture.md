# Designing one codebase for structurally different businesses

The concrete case this comes from: the same app now runs a restaurant POS (comanda, caja, stock, recipes) and a property-rental manager (properties, tenants, contracts, collections) — two businesses that share almost no domain vocabulary — without forking the codebase. The core insight: don't design "a restaurant app" and hope it generalizes later. Design the *shared skeleton* (who's logged in, what company are they in, what can their role see) as its own layer from day one, and let each business type ("vertical") be a set of tables + screens that plugs into that skeleton.

## The shared skeleton (build this once, reuse for every vertical)

- **`empresas`** — one row per tenant, with a `vertical` column (`'restaurante'`, `'alquileres'`, whatever comes next). This is the only place "which kind of business is this" gets decided.
- **`usuarios.nivel`** — a small, fixed, vertical-*independent* vocabulary (`platform` / `owner` / `staff` / `inventory` or similar), separate from `usuarios.rol` which stays free text and vertical-specific (`cajero`/`mozo` for restaurante, `cobro` for alquileres — whatever reads naturally to that business's staff). `nivel` is the only thing new RLS policies should ever check directly; `rol` is a per-vertical label with no structural meaning to the database.
- **`roles`** (catalog: vertical + name), **`permisos_rol`** (default module visibility per role), **`permisos_usuario`** (per-user override/exception). None of these three get queried by RLS policies directly — a page/report-level helper function (`usuarioTieneModulo()` client-side, `current_tiene_modulo()` as its SQL mirror) resolves them once per page load. Every RLS policy and every RPC that gates a whole module calls that one function — never re-derive the same logic ad hoc in a second place, or the two will drift and one of them will be the one nobody remembers to update.
- **A generic `documentos`/file-attachment table**, if the product needs file uploads anywhere, scoped by `(entidad_tipo, entidad_id, modulo)` rather than one bespoke table per feature that needs a file. Two features sharing an `entidad_tipo` (e.g. a "property photo" feature and a "property document" feature both attaching to the same `inmueble_id`) need the `modulo` discriminator in that key, or one feature's rows leak into the other's list.

## What's safe to build per-vertical, cheaply, on top of that skeleton

Everything business-specific: the actual domain tables (`productos`/`recetas` vs. `inmuebles`/`contratos`), the screens, the reports. Because auth, permissions, multi-tenancy isolation, and the module-visibility mechanism are already solved once, a second vertical is mostly "new tables + new screens," not "rebuild the foundation." That's the whole payoff of doing the skeleton work up front — the *cost* of adding a third business type should trend toward "a few weeks of domain-specific screens," not "another full rewrite."

Two verticals sharing infrastructure (e.g. both feeding the same `reportes` route, both listed side-by-side on the same `dashboard` tile grid) is fine and expected. What's *not* fine is one vertical's screen reaching into another vertical's tables or assuming something about a user that's only true for one business type — keep the isolation as strict between verticals as between tenants, even though it's not a security boundary in the same sense (it's a maintainability one: touching restaurante code should never require reasoning about alquileres, and vice versa).

## Gating rules worth getting right the first time

- **Module-level gating (`current_tiene_modulo('comanda')`) is for "can this role see this screen at all."** It is not fine-grained enough for actions with real financial/legal weight inside a module everyone with that module can otherwise use freely. A cashier with the `comanda` module can confirm sales all day — but voiding a sale after the fact (money already counted in a shift close) or overriding a delivery commission rate are different, higher-stakes actions that need their own explicit `current_nivel() = 'owner'`-style gate on top, not just "has the module."
- **Toggling a module off for one user is usually a *delete*, not an insert with `permitido = false`** — if `permisos_rol` already grants a module by default for that role, "block it for this one person" means inserting an *override* row, and "restore the default" means deleting that override, not inserting a positive one. Read which direction the default points before writing the toggle logic, or a "disable" button will silently do nothing (there was nothing to override) or a "re-enable" button will insert a redundant grant that already existed implicitly.
- **A brand-new module being enabled for every tenant in that vertical the moment its migration runs** is sometimes fine (a demo-only tenant with no real staff won't be confused by five new tiles appearing) and sometimes not (a tenant with real staff mid-shift). Check whether the vertical actually has live operational users before deciding a blanket rollout is harmless — "no real client is operating on this yet" and "this is in production" are different claims; confirm which one is actually true rather than assuming production access implies real usage.
- **A later, unrelated feature migration can silently reintroduce a role check that an earlier migration deliberately removed.** Real case: a table's RLS policies were migrated from role-based to pure module-gating on purpose, so that granting a module via `permisos_usuario` would be sufficient regardless of the user's `rol`. Months later, an unrelated feature migration on the *same* table added `and current_rol() in ('cajero','administrador')` back onto those same policies — nobody was touching RLS on purpose, it just looked like a reasonable-sounding extra safety check to bolt on while adding a new screen. The effect: a user with a different role (e.g. `deposito`) explicitly granted that module could no longer read the table, silently breaking the "a module grant is enough, independent of role" invariant for anyone outside the hardcoded list. Caught by a pre-existing integration test asserting exactly that invariant — not by review, which read the added condition as strictly-more-restrictive-therefore-safe. **Before adding any condition to an RLS policy on a table already migrated to module-gating, check why the current policy looks the way it does** (read the migration that set the pattern, or `git log`/`git blame` the policy) — the absence of a role check is very often a previous, deliberate fix, not an oversight to "restore." Once one such regression turns up, grep every other policy on that table, and on sibling tables that went through the same module-gating migration, for the same reintroduced shape.
- **A new vertical that extends a shared function or view must be proven harmless to the existing vertical by construction, not by hope.** The retail vertical added a branch for its own sales and customer payments to the cash-close function and the live-balance view that the restaurant already uses. The safety argument, written into the migration: retail rows attach only to shifts with a non-null `local_id`, restaurant shifts have `local_id NULL`, so the new branch can never see a restaurant shift; and the view keeps its column names (`create or replace view` cannot rename a column, and the restaurant reads `ventas_efectivo`, which now also includes payments). Put that argument in the migration header and re-run the existing vertical's tests. Later fixes to the shared object must start from the *live* definition, not from the version an earlier audit cited — an audit written before the new vertical merged described a cash-close function that no longer existed (`money-and-ledger-integrity.md` #7). Sibling tables shared between verticals (shifts, cash movements) also need the vertical-wide checks — a `NaN` guard on every numeric column had to include them.
